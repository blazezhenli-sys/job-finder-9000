# Hiring Signal Discovery

Self-hosted, deterministic hiring-signal monitoring with company social activity for Bluesky and Mastodon, plus a separate ATS listings stream for Greenhouse, Ashby, and Lever. It runs a Fastify dashboard and durable background worker against PostgreSQL. No browser session is needed for ingestion.

## Quick start

1. Copy `.env.example` to `.env`, change `DASHBOARD_PASSWORD`, and set `APP_PORT` if port 3000 is already in use.
2. Run `docker compose up -d --build`.
3. Open `http://your-server:3000` and sign in with the configured basic-auth credentials.

Coolify can deploy this repository as a Docker Compose project. Set `APP_PORT` to the host port you want to publish; the application remains on internal container port 3000. Keep the Postgres volume persistent. Set the same environment variables in Coolify; SMTP values stay server-side and are never returned by the API.

The Compose stack also includes RSSHub with bundled Chromium at `http://your-server:1200` by default; change `RSSHUB_PORT` if that host port is already in use. RSSHub uses the persistent `rsshub-redis-data` volume for its Redis cache.

For local development, run PostgreSQL, set `DATABASE_URL`, then use `npm install && npm run dev`. Set `DEV_MODE=true` to enable the “Load sample posts” action in the dashboard. The app runs migrations automatically at startup.

## Architecture and limitations

- `src/sources` contains the legacy global opportunity adapters. The old Posts stream is no longer started by the worker; company social activity is collected separately from discovered Bluesky and Mastodon accounts.
- `src/pipeline.ts` normalizes text, applies editable phrase/regex rules, extracts source evidence, and deterministically classifies each match as direct hiring, service request, employee referral, firsthand announcement, aggregated listing, or uncertain. Signal quality is kept separate from legacy score fields; rule weights contribute to transparent signal-quality evidence, while discovery remains broadly industry-agnostic rather than requiring an instance-specific vocabulary. There is no LLM classification.
- Every persisted post retains its original source URL, contact methods, classification reasons, and an author profile. Aggregated posts remain available through the category filter and are excluded from notifications when suppressed. Author classifications and an exact account/domain/text aggregator registry are editable in the dashboard.
- Location requirements are extracted conservatively from explicit wording: work mode, named places, allowed/restricted scope, time zones, and the source evidence used. This is source metadata only; the application does not assume a user location or score listings against one.
- The Listings tab is an independent pipeline. It automatically polls Remotive’s public remote-jobs API, and can optionally poll Adzuna when `ADZUNA_APP_ID` and `ADZUNA_APP_KEY` are configured. You can still add public Greenhouse, Ashby, or Lever boards by provider and identifier/URL. The first successful poll establishes a baseline, and later new postings can enter a separate email notification queue. Each listing retains the source page and direct application URL, plus the original employer, department, location, work mode, employment type, seniority, compensation, freshness, and saved/applied/dismissed state. The Listings view can filter by employer, department, employment type, seniority, location/region, salary currency and minimum salary, provider, status, and work mode.
- Company Profiles build on the existing `employers` registry rather than creating a duplicate company table. The Companies view summarizes active listings, optional engineering specialties and technologies, recent post-initial observations, work-mode/employment-type counts, ATS boards, and active openings. Successful board polls now record company activity history without treating an initial snapshot as historical hiring. Profiles also expose evidence-backed hiring signals, a bounded activity-based prospect score with contributing factors, and lightweight private prospect status/notes. Company metadata fields are available for later verified enrichment and manual correction; ATS slugs are not treated as authoritative company identity.
- ATS board discovery is a separate resumable job. It harvests Greenhouse, Ashby, and Lever URLs from Internet Archive CDX, falls back to Common Crawl, supplements recent runs with urlscan, extracts/deduplicates board identifiers, validates candidates with lightweight `HEAD` requests, and imports only validated boards. Archive responses are streamed rather than buffered as one complete payload; the cursor records the current provider/domain, archive rows, candidate count, and last URL for live monitoring. URLs found in existing or newly ingested Posts are also recorded, including aggregator-classified posts. Discovery stores source, attempts, status, progress, and retry timestamps in PostgreSQL; it never imports historical jobs or creates notifications.
- `src/worker.ts` is the always-on worker loop. Docker Compose runs a one-shot migration container, then the API and worker as separate containers from the same image; `start:web` and `start:worker` are also available for separate services. The worker owns listing polling, company enrichment, and company social polling in the same container. `DB_POOL_MAX` controls the PostgreSQL pool per process, and the Compose worker uses a smaller pool than the API. Set `RUN_MIGRATIONS=true` when running a standalone web/worker process without the migration container.
- PostgreSQL provides idempotency, notification retry state, source health counters, and restart recovery. Irrelevant matched-free posts are not stored; a configurable retention task removes old opportunities.
- Legacy global source settings remain supported for compatibility, but no new global social opportunities are ingested. Mastodon company polling accepts the same `MASTODON_ENDPOINTS` and `MASTODON_TOKENS_JSON` mapping, with legacy `MASTODON_INSTANCES` and `MASTODON_ACCESS_TOKEN` support for one endpoint.
- Listings are enabled by default and poll every hour; configure `ENABLE_LISTINGS`, `LISTINGS_POLL_INTERVAL_MS`, and the bounded `LISTINGS_POLL_CONCURRENCY` worker count as needed. A board’s initial snapshot does not generate notifications, preventing a newly added board from flooding the inbox. Remotive is polled every six hours by default because its public feed is delayed and intended for low-frequency access; configure `REMOTIVE_POLL_INTERVAL_SECONDS` if needed. Adzuna supports configurable countries, query, location, and poll interval through the `ADZUNA_*` variables.
- Discovery is enabled by default and runs an initial full job, then recent jobs daily. Configure `ENABLE_LISTING_DISCOVERY`, `LISTING_DISCOVERY_INTERVAL_MS`, and the bounded `LISTING_DISCOVERY_VALIDATION_CONCURRENCY` worker count; trigger a manual full or recent run with `POST /api/listing-discovery/jobs` and inspect progress with `GET /api/listing-discovery/jobs`. Validation requests still use a shared 250ms start-rate limit, retries, and resumable candidate state. The reference implementation’s large generated board cache was not imported because it has no per-record provenance/freshness metadata; discovery generates our own local, auditable registry instead.
- The Market section is a separate observability dashboard over Listings. It defaults to a stable-cohort, 90-day view with server-rendered SVG volume/share charts, new/removed flow, ranked dimensions, coverage, signals, and evidence drill-downs; the Listings tab remains the record-level search surface. `GET /api/market/dashboard` returns the dashboard payload and `GET /api/market/drilldown` returns contributing companies plus paginated listing evidence. The existing Market summary/filter endpoints remain available for detailed exploration. Listing classifications are deterministic and versioned; technologies are explicit mentions from a database-backed alias taxonomy, not proof of production usage or a confirmed requirement. `GET /api/market/taxonomy/technologies` and `PATCH /api/market/taxonomy/technologies` expose taxonomy maintenance.
- Temporal analytics are deliberately conservative. The first successful board poll is a baseline; it creates no historical “new listing” activity or notification. Later successful polls record append-only listing events, while missing listings require three consecutive successful observations before removal. Daily snapshots are idempotent and expose both the full observed index and a `stable_28d` cohort (at least 25 successful observation days in the preceding 28-day window). Stable-cohort changes are observed posting changes, not confirmed hires, and coverage fields remain attached to trends and signals.
- Company daily snapshots retain active/new/removed/remote/contract counts plus specialty, technology, employment-type, and work-mode composition maps. The worker persists deterministic company and market signals only after minimum monitoring history; signals include supporting listing IDs, explanations, comparison windows, sample sizes, and data-quality notes. Signal evidence can be opened from the Market view and is always linked back to the original listing source.
- Company profiles also collect original public posts from discovered Bluesky, Mastodon, and YouTube accounts through their native public feeds, plus LinkedIn and Facebook accounts through RSSHub. Bluesky/Mastodon/YouTube polling keeps the existing 15-minute schedule and concurrency; the RSSHub scheduler checks for newly due LinkedIn/Facebook accounts every hour, while each RSSHub account is polled every three hours with one browser-backed request at a time and no older-feed pagination. RSSHub rate-limit responses honor a longer `Retry-After` when provided, otherwise use a one-hour cooldown and stop further requests for that platform during the current cycle. All social activity retains 14 days of posts. The Tasks view groups social polling, listing polling, and company enrichment queues into sub-tabs; configure `ENABLE_COMPANY_SOCIAL_ACTIVITY`, `COMPANY_SOCIAL_POLL_INTERVAL_MS`, `COMPANY_SOCIAL_CONCURRENCY`, `COMPANY_SOCIAL_BACKFILL_LIMIT`, `COMPANY_SOCIAL_RETENTION_DAYS`, `RSSHUB_BASE_URL`, `COMPANY_SOCIAL_RSSHUB_SCHEDULER_INTERVAL_MS`, `COMPANY_SOCIAL_RSSHUB_POLL_INTERVAL_MS`, `COMPANY_SOCIAL_RSSHUB_CONCURRENCY`, `COMPANY_SOCIAL_RSSHUB_TIMEOUT_MS`, and `COMPANY_SOCIAL_RSSHUB_RATE_LIMIT_COOLDOWN_MS` as needed.

## Tests

`npm test` covers normalization, rule detection, scoring, deduplication semantics, timestamp handling, and notification eligibility. `npm run build` verifies the production TypeScript build.
